# P7U R4 — stock 20260311 boot/NV geometry correction (20 Oct 2026)

Status: **source-only correction and private read-only evidence; NOT FLASH-READY.**
Target: the single production **SLZB-06P7U R1.73 / CC2652P7**. Do not use
this decision with P10, MR4U, 06P7 (non-U), or an unverified capture.

Private image SHA-256:
`ecf1e46b56f0640dede870a2b1cc56604fb9aa454c7e40c984e09d8a8a712299`.
Never publish the image, underlying network identifiers, records or keys.

| Range | Verified current role | Correct R4 rule |
|---|---|---|
| `0x00000..0x2DFFF` | Signed MCUboot application (header at zero) | R4 APP-only payload may occupy only its approved low sectors |
| `0xA0000..0xA3FFF` | Erased | Do not interpret as restored NV; available only for separately designed migration |
| `0xA4000..0xABFFF` | **Four active TI NVOCMP v3 pages** | R4 current-network profile must use this exact 32-KiB region |
| `0xAC000..0xADFFF` | Resident executable boot manager, valid ROM-selected vector | **Never NV**; any replacement requires distinct approval |
| `0xAE000..0xAFFFF` | Boot-related content and final CCFG | Preserve unchanged; no CCFG erase/program under existing authorization |

Relevant CCFG fields: `IMAGE_VALID_CONF=0x000AC000`,
`BL_CONFIG=0xC5FE0FC5` (DIO15 low ROM backdoor),
`ERASE_CONF=0xFFFFFFFF`, all four `CCFG_PROT` words `0xFFFFFFFF`.
That is **no CCFG-configured sector write protection**, not proof that every
live flash/ROM operation will succeed. The fitted signed MCUboot image header,
signature and embedded ECDSA-P256 public key verified offline against the image.
This **does not** prove the resident loader's policy rejects unsigned images.

Stock NV page states are `FULL, FULL, ACTIVE, DESTINATION`; modes are
`F8, F8, FC, FF`. The independent C admission scanner at the *correct base*
read **892 CRC-valid records / 779 active compressed identities**, with no
duplicate-active failure, and classified **FORMED_CANDIDATE**. No write, erase,
reset or RF action occurred. Formed candidate is **not** coordinator state 9
or security/counter acceptance. The pre-existing 512-identity preflight limit
was insufficient and is now 1024; private and synthetic 779-ID probes pass.

## Consequence for the existing R4 artifacts

The historical `P7U_R4_FULL_NV4` native profile assumes
`0xA6000..0xADFFF`. **It must never be flashed onto the current stock
20260311 layout**: it would miss NV at `0xA4000` and can overlap the boot
manager at `0xAC000`.

The source-only geometry correction is
`qualification/p7u_stock_20260311_nv4_geometry.py`:
1. Pin the private capture/hash, current CCFG and four page headers.
2. Compose existing pinned TI 8.33.00.16 B0–B4 source.
3. Change only the SysConfig NVS base and linker NV base from `0xA6000`
   to `0xA4000`; keep `NVOCMP_NVPAGES=4`, size `0x8000`, app ceiling
   `0xA0000` and CCFG sector `0xAE000`.
4. Select the B1 bridge's new explicit `--nv-base 0xA4000` option. The
   bridge source check is implemented and tested, but the native build,
   TI host reader, provenance receipts and APP writer binding to this
   geometry are **NOT yet complete**.

The source-only CI workflow now first verifies the immutable historical
A6000 overlay against its upstream TI blobs, then requires its hash-bound
receipt before remapping disposable source copies to **A4000** and reducing
linker app size from **A6000 to A0000**. Its bridge uses explicit
`--nv-base 0xA4000`; new tests verify both success and fail-closed receipt
rejection. These checks still do **not** validate compiled/native behavior
or on-device R4 startup. The historical A6000 assertion is deliberately a
pre-remap source-integrity gate, not evidence that A6000 is safe to flash.

The old profile remains versioned for historical reproducibility, not for
current hardware eligibility.

## Lowest-risk migration decision under review

A resident single-sector `0xAC000` handoff is *potentially* preferable to
a one-way CCFG `0xAC000 -> 0` word program because it keeps the last CCFG
sector byte-for-byte intact, and the old 8-KiB boot sector can be restored
through the already demonstrated ROM-BSL read/program route. But prior
handoff experiments **did fail to start ZNP**; do not treat that route as
qualified. It must be reviewed again with the corrected NV geometry and
current native image. Replacing the resident manufacturer boot stage also
changes its code-signing trust boundary until stock rollback.

The alternative CCFG bit-clear in-place leaves old boot code physically
present, but restoration requires erasing/reprogramming the entire last
8-KiB CCFG sector (0 -> 1 reversal). That remains a distinct, higher-risk
operation. Neither route is authorized by the old APP-only approval.

Minimum next code gate: bind the opted-in B1/NV bridge and source manifest,
rebuild the corrected candidate reproducibly, run the pinned TI host NV reader
against the private pages **read-only**, and prove a bounded stock rollback for
the exact boot target. After that, request explicit owner approval describing
the single upper boot sector or CCFG field being changed. Only then consider a
physical flash. No more counter increments, full restore, or Z2M transport
changes merely to test geometry.
