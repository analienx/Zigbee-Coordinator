- Stage 2: compaction returned 0 — `capture(status==NVINTF_SUCCESS ? 2u : 3u,

### T832R6Nv_capture semantics (EXIST/NOTFOUND excluded)

- Every capture bumps `sequence` twice (odd-while-writing tearing marker,
  `nv_r6_probe.inc:7,41`; exporter skips odd, `r6_nv_export.inc:11`),
  overwrites last `stage/requested/status` (:8-10), and copies full topology
  (:31-40: pages/head/tail/active/offset/ready/offsets/states).
- `first_failure`/`first_failure_requested` latch ONCE per boot on the first
  nonzero status at stage 3/6/8 (:16-20), EXCEPT stage-8 EXIST(13)/
  NOTFOUND(10) (:17), "ordinary lookup/create outcomes" (:14-15) whose raw
  status is still preserved in the last-stage fields. The exclusion applies
  ONLY at stage 8 (stages 3/6 cannot produce EXIST/NOTFOUND: compact/addItem
  return compactStatus/NVINTF-flash codes). Hosted proof of the exclusion:
  `nv_population.c:71-75`. Nothing ever clears the latch (sticky per boot).
- Export (`r6_nv_export.inc`): `NV_RESULT a=stage,b=requested,c=status`
  (:35), `a=7,b=init_action,c=first_failure` (:36), `a=9` reject latch (:40),
  sticky `NV_FAULT a=8,b=first_failure,c=first_failure_requested` on the
  CRITICAL ring (:43). Topology/counters describe the LAST API boundary,
  never the first-failure instant (`diag_schema.json:284`).

### 27-byte failure semantics — what (a8,b1,c27) can and cannot be

- Decode: a=8 → sticky first-failure export (`r6_nv_export.inc:43`); b=1 →
  first nonzero latched status; c=27 → `requested` of THAT SAME latching
  capture (`nv_r6_probe.inc:18-19`).
- Elimination (source-proven): initNvApi stage 8 passes requested=0
  (`r6_observer.py:42`) and delete stage 8 passes 0 — both EXCLUDED (c=27).
  The R10 reject-path oracle shape is `NV_FAULT(8,init_status,0)` +
  `NV_RESULT(8,0,status)` (`verify_startup_guard.py:2018-2040`) — c=0, NOT
  the D2 shape.
- Remaining candidates, INDISTINGUISHABLE in shipped D2: (a) stage 3 with
  `NVOCMP_compact` returning 1=SRCDONE and nBytes=27 — a SUCCESSFUL
  compaction (TI test nvocmp.c:4145) for a 27-byte need = 20-byte item +
  7-byte header (iLen, nvocmp.c:2919): an observer classification artifact,
  NOT a storage failure; (b) stage 6 with `addItem` returning
  NVINTF_FAILURE(1) for a 27-byte item — genuine item-write failure; (c)
  stage 8 with an API returning NVINTF_FAILURE(1) and len/minAvail=27
  (create/update/write of a 27-byte item, or explicit compact minAvail=27).
- D2 records only the LAST stage (`NV_RESULT a=stage`), never the latching
  stage; no API/op/item/caller field exists. `NV_COUNTERS a2`
  (compact_failures) increments ONLY in case (a) — the full D2 frame set
  could hint, but M0's evidence is the triple alone: attribution UNKNOWN.
  NEVER assign cross-reset causation (brief + HA#73c6066617054).
- REGRESSION vs R0: legacy R0 compaction hook tested
  `status == NVOCMP_COMPACT_FAILURE ? 3u : 2u` (`apply_diag.py:707,718`),
