# Next repair: preserve the first warning and first overdue operation

## Priority and scope

P0 is a host-only first-warning snapshot. P1 is a separately qualified radio
operation-age detector with independent execution-context progress. P2 is an
independent USB/UART boundary observation, including ESP counters only when
the exact board/backend can supply them. Earlier V5 sampling is supporting
work, not a substitute for identifying the first operation that stops.

The installed `e3a0f3b7` image and current host are not changed by this source
candidate. No firmware restore, reset, serial takeover or induced flood is
part of qualification. Public builds run on GitHub, with focused changed-path
checks and actual host compilation rather than another broad review campaign.

## Implemented P0 candidate

The existing ZNP owner records a bounded 16-transition history of offered
production SREQs and their acknowledgements/timeouts. It stores only monotonic
times, a host-lifetime operation ordinal, subsystem, allowlisted operation
class, queue/map counts, and raw-stream/parsed-frame/error counters. Payloads,
device identities and error strings are excluded. Per-operation history reads
are O(1); full waiter accounting is sampled at the warning boundary.

The first warning is captured while a normal SREQ remains pending, on a slow
acknowledgement, or on its exact Waitress timeout. The host warning threshold
is two thirds of the request timeout, capped at four seconds. It is explicitly
**a host warning, not proof of a radio fault**. Monotonic elapsed time and timer
lateness remain visible, so an event-loop delay cannot be relabelled as a
measured radio stall. Diagnostic F0/F2 requests do not trigger a production
warning.

The frozen snapshot includes current pending-operation timing, host stream RX
and parser timing, bounded history, current adapter/mutex/waiter accounting,
and a copy of the last durably acknowledged V5 flight with its receipt and
monotonic age. A flight merely queued to a worker is not accepted as durable.
The first warning consumes a reserved worker slot, uses existing asynchronous
fsync/hash-chain persistence, and never synchronously writes disk in the owner.
Optional evidence failure cannot change a production request's result.

The first warning marks the next existing flight opportunity due; it does not
send a radio request. V5 also uses the first normal sampling slot. Busy vetoes
retain capture demand, alternating with a V4 slot so V4's bounded admission
cannot be starved. Submitted failures retain the existing cooldown, progress
and quarantine rules and remain distinct from pre-wire skips.

FIRST_WARNING is a separate journal kind. It does not count as native VALID
or a V5 FLIGHT pair. The versioned passive half-hour exporter preserves the
snapshot and flags it as a warning, retaining all existing congestion/flight
projections and historical reports.

## P1 requirements carried into the radio repair

The first native prototype was retained privately for revision; it is not in
this host-only candidate. A blanket three-second queue/MT threshold and an
unknown MT command are insufficient for the requested detector.

The radio change must track a specific operation through entry and completion,
with stage ownership/generation, monotonic entry time, pending-response state,
and frozen preceding events. Each stage needs a justified budget. An ordinary
four-second host response is not automatically an overdue radio MT handler.
A detector must run from a pinned safe timer/interrupt context rather than the
blocked MT or NPI task it observes. Separate per-context first observations
must prevent early queue congestion from erasing a later MT or TX stall.

NPI task progress, a source-qualified Zigbee stack task-loop heartbeat, and UART
TX completion must be distinct. An MT entry/exit pair is not a background stack
heartbeat. Heap low-water, stack margins and boot-identity diagnostics are
included only after validating the real providers and runtime cost. Unknown
capabilities remain unavailable. No automatic recovery or NV persistence is
added. A frozen RAM record is lost on reset and may remain unreadable after a
hard hang; source tests cannot establish otherwise.

## P2 boundary dependency

The public [SLZB-OS ZB API](https://github.com/smlight-tech/slzb-os-scripts/blob/main/docs/modules/zb.md)
provides socket callbacks and byte reads that require suspending the normal
stream. It does not provide independently qualified UART-RX/USB-forwarded
counters for the installed P7U backend. Such reads must not steal the stream.
The exact SLZB-OS v3.4.3.dev1 backend/build is needed for instrumentation.

A bridge provider must expose successful UART RX, UART overruns/errors,
successful USB-forward completion and failures, counter/reset epoch,
monotonic sample time, and the actual physical route through management.
Some USB routes may bypass ESP; those ESP metrics must be unavailable, not
zero. Comparable windows and uninterrupted epochs are required before
attributing a missing boundary. No Berry script or bridge image is installed
by this host change, and no vendor notification is sent.

## Qualification and delivery

Required P0 evidence is actual pinned owner/Z2M compilation, changed-path
runtime checks for pending/slow-ACK/timeout capture, no extra wire request,
no production error changes, bounded immutable history, ACK-only flight cache,
durable replay/privacy validation, and half-hour projection of the real warning
fixture. Deployment needs an exact host artifact and fresh guarded host-only
handoff; it does not require a radio flash. P1 and P2 remain part of the next
repair and cannot be marked complete by delivering P0 alone.
