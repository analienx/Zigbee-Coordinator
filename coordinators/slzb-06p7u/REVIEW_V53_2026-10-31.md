# SLZB-06P7U V53 firmware review — 31 October 2026

Long-term reliability review of the firmware installed on the production SLZB-06P7U on 31 October 2026, and of the host tooling that installed it. It records findings only. It authorizes no hardware action, and it does not qualify V53 (see the gates in [`README.md`](README.md)).

**Method.** The deployed C is not stored as files. It is emitted by the Python stage scripts listed in [Where the firmware lives](#where-the-firmware-lives), which edit a pristine TI SDK checkout. The review read the C each stage inserts and checked the surrounding TI code at the pinned SDK commit. Pristine `osal_port_timers.c` matched the SHA-256 that V52 pins. The repository test suite ran on the combined firmware and delivery tree: **1057 passed, 31 skipped, 0 failed**, after two stale assertions were corrected (finding F10). On `main`, where tests of removed earlier-version code went with it, the suite is 924 passed, 31 skipped.

**Not covered:** no native TI build, no compilation of the composed image, no hardware. B0–B3 (board, NV, security fusion) and the F2 v4.2–v6 diagnostic layers were reviewed only at the level of their interfaces with V47–V53.

## Summary

- **The V53 fix is correct, and it targets the measured cause.** Every NV mutation on this build goes through the wrapped function table, NVOCMP serializes the driver, and the generation guard closes the read-versus-write race. One gap: cache hits bypass B1's fail-closed NV HOLD (F3).
- **V52 is correct.** Expired OSAL timers are freed under the same Hwi-off critical section TI uses. The unlocked empty-list fast path is benign.
- **Biggest current risk is operational, not in the image.** The hang-evidence capture and the flash driver only work with the uninstalled custom host. In a real hang today, no firmware evidence can be captured (F1).
- **Biggest long-term risk is accumulated mitigation.** V44–V50 changed TI's scheduling contract to keep the coordinator serviceable while the Stack task was saturated. V53 removed that saturation (1 % busy). The permanent NPI-above-Stack priority (F2) and the aging scheduler remain in the image with only about four hours of soak.

## Findings

Ranked by long-term reliability impact.

### F1 — High: hang evidence and the flash driver only work with the retired custom host

- `host/flash/p7u_hang_evidence_once.py` requires `ha.inspect()` of `app_local_p7u_r4_native_host`. When that container is absent, `absent_owner()` requires the uninstalled app's Supervisor metadata and the `local_p7u_r4_owner_inspector` container. Under the official Zigbee2MQTT app, every one of these raises `Hold`.
- The capture therefore **fails closed**: it never opens the TTY, so it cannot become a second UART owner. That is safe. But it means the V51–V53 onset record, trend rings and NV-cache evidence cannot be read before a ROM round trip wipes RAM.
- `tools/p7u_ha_flash_driver.py hang` runs `ha apps stop local_p7u_r4_native_host` without checking the result. It then calls `restart_host()`, which starts the same uninstalled app. It never stops the official app, so a manual stop is still needed before any ROM step.
- `HANG_RECOVERY_RUNBOOK.md` section D starts `local_p7u_r4_native_host`. It must be re-written for the official app before it is used again. This is open item 1 in the [status](STATUS_2026-10-31.md).

**Recommendation:** parameterize the owner (official app slug and container) in `p7u_pr154_ha.py` and the driver. Check the result of every `ha apps stop/start`. Keep the zero-TTY-holder proof, but source it from something that is still installed. Until then, the runbook skips the capture step (now noted there).

### F2 — Medium-high: the NPI task permanently outranks the Stack task

- TI runs Stack at priority 5, NPI at 4 and MAC at 3. V46 raised NPI to 6 only while a framed SRSP was pending.
- V50 replaced V47's 90 s window with a **sticky** floor. Once B1's retained-start event arms it, `B4_V47_ActiveLocked()` returns `B4_V47_Armed` for the rest of the boot. Only a B1 HOLD lowers it. The stage refuses to apply if anything clears `B4_V47_Armed`.
- Any CPU-bound NPI-side path, such as a UART RX error storm or an MT handler that runs long in the NPI context, now starves the whole Zigbee stack instead of only the host link.
- B1 already removed the one known NPI self-repost spin (`patch_management.py`, "NPI flow-off UART busy self-reposting starves MT"). That lowers this risk but does not bound it.
- V50 was added because the Stack was CPU-saturated. V53 measured the Stack at about 1 % busy, so the floor's original reason no longer applies.

**Recommendation:** after a multi-day soak confirms the Stack stays well below the 50 % calm threshold (B1E4/B1E5), evaluate a source change back to V46 transient-only boosting. It needs full native and physical requalification.

### F3 — Medium: V53 cache hits bypass B1's fail-closed NV HOLD

- B1 makes the driver fail closed once `b1_nv_runtime_hold_active()` latches. `NVOCMP_read`, `readHeader`, `write` and `erase` all refuse and re-latch (`patch_nv_integrity.py`).
- `B4_V51_NvReadItem` serves a hit before reaching the driver. After a HOLD, up to eight previously read items keep returning `NVINTF_SUCCESS` from RAM. These include the active NWK key, which `ZDSecMgrReadKeyFromNv` reads as offset 1, length 16 of `ZCD_NV_NWK_ACTIVE_KEY_INFO` for secured frames. MAC data requests are still refused during HOLD (`ZMacDataReqSec`), so TX stays blocked.
- This weakens the "NV fault means no NV data" invariant. It does not corrupt NV.

**Recommendation:** in `B4_V53_Lookup`, return a miss when `b1_nv_runtime_hold_active()` is set. Also invalidate the cache from `b1_nv_runtime_hold_latch()`. Small, source-only, needs requalification.

### F4 — Medium: storm-era mitigations and diagnostics remain in the production image

- V48 forced ZDApp selection while INIT or START is pending in the retained attempt. V50 aging serves any service passed over 4 times. Both permanently change TI's lowest-index-first service order.
- F2 v4.2–v6 and B1E1–E7 evidence add Hwi-off critical sections on every Stack dispatch (about 4), every MAC callback (1) and every NV call. An NV read miss takes 5 sections; a hit takes 1.
- At about 1 % Stack load the cost is small. But each layer is extra state, review surface, and NPI-stack (1024 B) pressure in the static snapshot buffers.

**Recommendation:** once the soak and F1 tooling exist, plan a simplification release. Keep B1, AF handoff, V43, V45, V52 and V53. Re-justify or remove V47/V48/V50 scheduling and any evidence page no longer read.

### F5 — Medium: the deployed C is hard to read and depends on pins outside `main`

- About 25 chained text-anchored patchers produce the image. They are well guarded (exact preimage hashes, single-occurrence anchors, compiled mutants). However, nobody can read the deployed `npi_task.c` or `zstackstartup.c` without re-running the pipeline against the TI SDK.
- The native workflow fetches the B2 donors `d13a48f…` (`b2_mto_fail_closed_overlay.py`) and `530a526…` (`b2_mto_nv_guard.py`) and the B4 donor `3231abb…` (`b4_native_patch.py`, `b4_v4_native_patch.py`) by SHA. They are reachable only from closed-PR refs (#121, #114, #110/#120/#138). The paired host source `2c2d96d…` is likewise kept only by PR #189/#197 refs.
- `main` carries the latest version only, so none of these commits are ancestors of `main`. PR refs are durable, but tags (`archive/r4-donor-*`, `archive/p7u-v53-paired-host-2c2d96d`) are planned as a second anchor; see the [branch audit](../../docs/BRANCH_PRUNE_AUDIT_2026-10-31.md).

**Recommendation:** for every future image, attach the composed `git diff` of the TI SDK (or the composed files) to the native-build artifact and the release receipt.

### F6 — Low: the cache lookup runs before the driver's parameter checks

Pristine `NVOCMP_readItemApi` returns `NVINTF_BADPARAM` for `pBuf == NULL || len == 0`. `B4_V53_Lookup` copies into `buffer` first. `len == 0` can never hit, because `Insert` rejects it. A NULL buffer with a cached length would fault. No caller in this build passes NULL. Fix together with F3.

### F7 — Low: a RAM copy of the active NWK key item

Up to eight ≤32-byte reads, the 16-byte active NWK key among them, live in `B4_V53_Cache`. Stock Z-Stack reads keys from NV on demand and clears local copies after use (for example `memset(zgPreConfigKey, 0x00, SEC_KEY_LEN)` in `zd_sec_mgr.c`). Lines are zeroed on every invalidation, and B1E7 exports only IDs and counts (verified in `B4_V53_NvCacheSnapshot`). Accept, but record it as a deliberate change to the key-at-rest posture.

### F8 — Low: inconsistent version labels

The installed V53 is on branch `fix/p7u-r4-v49-ready-npi-20261030`. Its PR #195 is titled "V52", and delivery PR #196 is titled "V52" but pins V53. Use the SHAs (and the tags, once pushed) from this review as the names of record.

### F9 — Low: evidence counters

- `B4_V52_Wraps` advances only at the end of a dispatch. A wrap is missed if no dispatch completes for about 11.9 h, which would itself be a hang.
- `B4_V52_Timers.freed` and `B4_V52_NwkBits[]` wrap instead of saturating.
- Evidence only; no functional effect.

### F10 — Info: stale tests fixed

`test_composite_b4_accepts_only_attested_b1_mt_sys` and `test_trace_armed_checkpoint_never_blocks_stack` asserted source text that had been refactored. Both failed on the firmware and delivery branches before they were combined. They now assert the current code.

## Verified correct

**V53 NV read cache** (`tools/r4_v50_stack_service.py`):
- **Complete invalidation.** At SDK `3615ad5d`, every NV call goes through `pZStackCfg->nvFps`, dereferenced on each call: `osal_nv.c`, every MT SYS NV/OSAL-NV handler, and `zcl_port` (which stores a pointer to the table). `sampleApp_task` is not started under ZNP.
- **No bypass in B1.** B1 adds no direct `NVOCMP_*` mutation; `patch_nv_integrity.py` only guards the driver's internal `write`/`erase`. Create, update, write, delete, compact, doNext and erase all invalidate before and after the driver call.
- **Race-safe inserts.** `NVOCMP_LOCK` is a `GateMutexPri`. The reader captures the generation before the driver read and inserts only if it is unchanged, so a read that overlaps any mutation is never cached. A 32-bit generation wrap is not reachable.
- **Exact matches only.** Hits require the same (system, item, sub-ID, offset, length). Only `NVINTF_SUCCESS` reads of 1–32 bytes are inserted. Critical sections are bounded (8 lines × 32 bytes).
- **Hooks install before first use.** They install once at Stack task entry, before `b1_sec_validate_restored()` and `stackInit()`. The table copy and swap share one critical section.

**V52 timers** (`tools/r4_v52_osal_timers.py`):
- `timerCb` runs in the Clock Swi. `OsalPortTimers_cleanUpTimers()` runs in tasks (Stack, and the MAC registration path) inside `OsalPort_enterCS()`, as TI's original code does.
- Prepending instead of appending is order-independent, because cleanup frees the whole list.
- The unlocked `NULL` fast path can only miss an entry that the next call frees.

**V45 SRSP reserve:** calling `NPITask_processStackMsg()` from the MT producer matches TI's own contract. That function takes `OsalPort_enterCS()` "to prevent higher priority tasks from also enqueuing".

**V48:** only already-posted `ZDO_NETWORK_INIT`/`ZDO_NETWORK_START` bits are selected, and only while B1's retained attempt is active. TI's ZDApp handler clears each bit it services, so this cannot livelock.
