# SLZB-06P7U R4 firmware review, all phases — V53 (31 Oct – 1 Nov 2026)

Long-term reliability review of every phase in the firmware installed on the production SLZB-06P7U on 31 October 2026, and of the host tooling that installed it. It authorizes no hardware action and does not qualify V53 or the V54 source fixes below (see the gates in [`README.md`](README.md)).

## Summary

- **No defect found in the root-cause fix or its supporting layers.**
  - V53's NV cache invalidation is complete on the composed tree.
  - V52's timer handling is correct.
  - V43–V46 (TX liveness, SRSP service, static reserve, priority) keep progress, ownership and bounds.
  - The SYS F0–F3 diagnostics and the B1 query parsers validate host-supplied lengths.
- **Fixed in source (V54 candidate, not built natively or flashed):**
  - The V53 cache now honours B1's fail-closed NV HOLD, including a HOLD latched inside the driver read (F3).
  - It never stores the TCLK seed (F7).
  - It never reaches the cache with a NULL buffer or zero length (F6).
- **Fixed in host tooling:** the flash driver's `hang` phase now refuses, before touching anything, unless the paired host it was written for is installed. It also checks the stop result (F1, partial).
- **New, latent: boot-time refusal before the configured capacity (F11).** The NV4 boot admission refuses to start at 1,024 distinct active NV items. The R4 profile itself preallocates tables up to about 820 items and allows 300 TC link keys. A network that grows toward its configured capacity would be refused on its next reboot. This needs a live measurement before it can be fixed safely.
- **Operational:** hang-evidence capture still cannot run under the official Zigbee2MQTT app (F1).

## Findings

Ranked by long-term reliability impact.

### F1 — High: hang evidence only works with the retired custom host (partly fixed)

- `host/flash/p7u_hang_evidence_once.py` requires `ha.inspect()` of `app_local_p7u_r4_native_host`. When that container is absent, `absent_owner()` requires the uninstalled app's Supervisor metadata and the `local_p7u_r4_owner_inspector` container. Under the official Zigbee2MQTT app, every one of these raises `Hold`.
- The capture therefore **fails closed**. It never opens the TTY, so it cannot become a second UART owner. But the V51–V53 onset record, trend rings and NV-cache evidence cannot be read before a ROM round trip wipes RAM.
- **Fixed:** the driver's `hang` phase used to run `ha apps stop local_p7u_r4_native_host` without checking the result, then try to restart the absent app. It now refuses up front.
- **Still open:**
  - `HANG_RECOVERY_RUNBOOK.md` sections C/D name the custom host and its startup observer.
  - Official-app support needs the HA app slug and container, and a still-installed zero-TTY-holder proof. Neither can be read from the repository.

### F2 — Medium-high: the NPI task permanently outranks the Stack task

- TI runs Stack at priority 5, NPI at 4 and MAC at 3. V46 raised NPI to 6 only while a framed SRSP was pending.
- V50 replaced V47's 90 s window with a **sticky** floor. Once B1's retained-start event arms it, `B4_V47_ActiveLocked()` returns `B4_V47_Armed` for the rest of the boot. Only a B1 HOLD lowers it.
- Any CPU-bound NPI-side path now starves the whole Zigbee stack, not just the host link. B1 already removed the one known NPI self-repost spin, which bounds the known case.
- V50 was added because the Stack was CPU-saturated. V53 measured the Stack at about 1 % busy, so the floor's original reason has gone.
- **But the floor also prevents a second failure.**
  - B1 turned TI's NPI RX-ring overflow trap (`for(;;)` in the ISR) into a **permanent transport HOLD**, which is a dead host link until reset.
  - Overflow only happens when the NPI task is starved while the host keeps sending.
  - So dropping the floor without also making RX overflow recoverable would re-expose a permanent hang.

**Recommendation:** after a multi-day soak, decide on V46-only boosting together with a recoverable RX-overflow policy. Today's sticky HOLD exists because a lost byte could let a corrupted MT command through a 1-byte FCS. Not changed here: both are behaviour changes that need native and physical requalification.

### F3 — Medium: V53 cache hits bypassed B1's fail-closed NV HOLD — fixed in source (V54)

- B1 makes the driver fail closed once `b1_nv_runtime_hold_active()` latches (`patch_nv_integrity.py`). V53 served cache hits before the driver, so after a HOLD up to eight items, including the active NWK key, still returned `NVINTF_SUCCESS` from RAM.
- A second path was found on the composed code. When B1's `NVOCMP_read` latches a fault mid-read, it zeroes the caller's buffer, and V53 could then cache those zero bytes.
- MAC TX is refused during HOLD (`ZMacDataReqSec`), which limited the impact.
- **Fix:** see the table above.

### F4 — Medium: storm-era mitigations and diagnostics remain in the production image

- V48 forces ZDApp selection while INIT or START is pending in the retained attempt. V50 aging serves any service passed over 4 times. Both permanently change TI's lowest-index-first service order.
- F2 v4.2–v6 and B1E1–E7 add Hwi-off critical sections on every Stack dispatch (about 4), every MAC callback (1) and every NV call (5 on a cache miss, 1 on a hit). V45 wipes 255 bytes and V53 up to 256 bytes inside a critical section. That's microseconds; UART2 RX is uDMA-driven.

**Recommendation:** after the soak and F1 tooling, plan a simplification release. Keep B1, AF handoff, V43, V45, V52, V53/V54. Re-justify V47/V48/V50 scheduling (see F2) and any evidence page no longer read.

### F5 — Medium: the deployed C is hard to read and depends on pins outside `main` (partly fixed)

- About 25 chained text-anchored stages produce the image. They are well guarded (exact preimage hashes, single-occurrence anchors, compiled mutants). `tools/p7u_compose_source_locally.sh` now lets anyone produce the composed patchset locally.
- The native workflow fetches the B2 donors `d13a48f…`, `530a526…` and the B4 donor `3231abb…` by SHA. They are reachable only from closed-PR refs (#121, #114, #110/#120/#138). The paired host source `2c2d96d…` is kept only by PR #189/#197 refs. Tags are planned as a second anchor; see the [branch audit](../../docs/BRANCH_PRUNE_AUDIT_2026-10-31.md).

**Recommendation:** attach `r4-final-ti-source.patch` to every native-build artifact and release receipt. The workflow already generates it.

### F11 — Medium (latent): boot admission refuses a network below its own configured capacity

- `nv4_readonly_admission.c` runs on every boot. It stops with `R4_NV4_SCAN_LIMIT`, a B1 NV HOLD, when distinct **active** NV items reach `R4_MAX_ACTIVE_IDENTITIES = 1024` (static `uint32_t live_ids[1024]`, 4 KB).
- The stock capture had **779** active items.
- B1's `b1_nv_prepare_retained_capacity()` (in `osal_nv.c`) then preallocates the R4 profile's table tails:
  - address manager 357 → 406 rows
  - device list 51 → 97
  - bindings 1 → 4
  - groups 1 → 16

  That's +113 at conversion.
- TC link-key entries (`ZCD_NV_EX_TCLK_TABLE`) are created per joined device, up to TC300.
- Estimate:
  - About 260 fixed items, assuming about one TCLK entry per current device.
  - 406 + 97 + 4 + 16 preallocated.
  - Up to 300 TCLK entries.
  - Total about 1,085 at full profile capacity, **above the 1,024 cap**.
- A healthy network that grows toward its configured size would therefore be refused on the next reboot.
- The read cap (30,000) is far above the worst case (about 6,500), so it is not a risk.
- **Not changed here, by design.** Raising the cap costs SRAM, and Z-Stack's OSAL heap is sized from leftover RAM. This build uses GPRAM, not an SRAM `tBuffer`, for NVOCMP compaction, so a RAM-neutral scratch would mean switching VIMS cache mode inside the boot-time scan. Both need a native link and hardware proof.
- **First step:** read the live `active_records` that B1 already records (`b1_management_note_nv4`) to see the real margin. Then choose between a measured cap raise (checked against heap low-water) and a GPRAM-scratch scan.

### F6 — Low: cache lookup before the driver's parameter checks — fixed in source (V54)

Pristine `NVOCMP_readItemApi` returns `NVINTF_BADPARAM` for a NULL buffer or zero length. V53 consulted the cache first, so a NULL buffer with a cached key would have faulted. No caller passed NULL.

### F7 — Low: key material held in the cache — reduced in source (V54)

- `b1_sec_validate_restored()` deliberately zeroes its local copies of the NWK key, active-key item and TCLK seed. Its reads went through the V53 cache, which kept those items (all ≤32 bytes) in RAM until the next NV mutation.
- V54 never caches the TCLK seed, from which every TC link key derives and which is not on the hot path.
- The active NWK key stays cached: it is the per-frame read that V53 exists to serve. Lines are zeroed on every invalidation, and B1E7 exports only IDs and counts.

### F12 — Low: a defined TCLK attribute is treated as corruption

`APSME_TCLinkKeySync` and `TCLinkKeyLoad` now latch a security HOLD on any `keyAttributes` value outside the handled set. `ZG_DISTRIBUTED_DEFAULT_KEY` (0xFC) is defined in `zglobals.h` but unhandled; pristine TI drops the frame. Nothing on a centralized coordinator assigns 0xFC, so this is strictness, not a live risk. Note it for any future restore tooling that writes TCLK entries.

### F13 — Low: READY is revoked for the rest of the boot if ZDO leaves the coordinator state

`b1_management_note_zdo_state()` revokes readiness, and requires fresh validation, if ZDO reports a non-coordinator state after READY. A later host startup request would then be refused. On a running coordinator the only exits are `DEV_COORD_STARTING` (needs a formation request, which B1 refuses after READY) and `DEV_INIT` (stack init), so this cannot fire in normal operation.

### F8 — Low: inconsistent version labels

The installed V53 is on branch `fix/p7u-r4-v49-ready-npi-20261030`. Its PR #195 is titled "V52", and delivery PR #196 is titled "V52" but pins V53. Use the SHAs (and the tags, once pushed) as names of record.

### F9 — Low: evidence counters

- `B4_V52_Wraps` advances only at the end of a dispatch.
- `B4_V52_Timers.freed` and `B4_V52_NwkBits[]` wrap instead of saturating.

Evidence only; no functional effect.

### F10 — Info: stale tests fixed

`test_composite_b4_accepts_only_attested_b1_mt_sys` and `test_trace_armed_checkpoint_never_blocks_stack` asserted refactored source text. Both failed on the firmware and delivery branches before they were combined. They now assert the current code.

## Verified correct (composed source)

**NV and security**
- **V53 coherency.** On the composed tree, the only NV tables are `pZStackCfg->nvFps` (wrapped) and pointer holders that dereference it (`osal_nv.c`, MT SYS NV handlers, `zcl_port`). B1 and NV4 are compiled into `nvocmp.c` and add no mutation of their own. NVOCMP serializes with `GateMutexPri`. The generation guard means a read overlapping a mutation is never cached.
- **NVOCMP init (B1).** NULL mutex, NVS handle or wrong geometry latch HOLD. NV4 admission is fail-closed. The only writes permitted at boot are TI's own init-journal replay.
- **`osal_nv_item_init` (B1).** Initializes only allowlisted empty table tails with erased bytes, verifies every written byte and latches HOLD otherwise. It never initializes over an existing item.
- **Security manager.** The per-frame paths (`ZDSecMgrReadKeyFromNv`, `APSME_TCLinkKeySync/Load`) latch HOLD only on local inconsistency: an out-of-range table index or an invalid stored attribute. A peer frame counter at `UINT32_MAX` is treated as an old frame, not a local fault.
- **Restored-network validation.** `b1_sec_validate_restored()` latches HOLD on every failure path before the Stack task returns. MT registration failure becomes a transport HOLD rather than a NULL-task crash.

**NPI transport and MT**
- **NPI TX (V44/V45/V46).** The NPI task is the sole TL writer, so the busy check under the critical section cannot race submission. `B4_V44_Pend` skips the pend only when `ProcessTXQ` can make progress, so it never spins. V45 slots are claimed and released under the critical section, bounded (4+250+1 ≤ 255 bytes) and never returned to the OSAL heap.
- **Message ownership.** `NPIFrame_frameMsg` always frees the incoming buffer, and every `processStackMsg` failure branch frees what it allocated, so the dynamic SRSP path cannot leak heap.
- **UART (B1/B4/V43).** In the pinned UART2CC26X2 driver, the read callback only reports `SUCCESS`/`ECANCELLED`, and `UART2_read` only fails on misuse. Line noise or framing errors therefore cannot trip B1's permanent transport HOLD. A write rejected synchronously clears `npiTxActive` (V43). B1 and B4 share one UART2 event callback, B1 last.
- **Host-facing parsers.** SYS F0/F3 require a 0-byte request, F2 exactly 8 or 9 bytes. The V50 op4 query checks the exact query size and prefix, and the page must be ≤ 5.
- **F2 v5/v6 diagnostics.** Fixed 16-entry rings and 160-byte pages, 4 ingress slots. Clock-Swi checkpoints read queue heads only under the critical section.

**Timers and scheduling**
- **V52 timers.** `timerCb` (Clock Swi) and `cleanUpTimers()` (tasks, Hwi-off critical section) are serialized as in TI's original code. The unlocked NULL fast path is benign.
- **V48.** Selects only already-posted ZDApp INIT/START bits during B1's retained attempt. TI's handler clears each bit, so it cannot livelock.

**Flash tooling**
- **ROM writer and operator envelopes.** `NV5_BASE = 0xA4000` equals the NV4 base. Writers touch only APP sectors below it plus the paired `0xAC000` handoff. The CCFG sector is excluded and its CRC checked after programming.
